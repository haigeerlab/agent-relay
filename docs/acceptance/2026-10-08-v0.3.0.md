## Probes (before the module, same machine)

- `thread-follower-start-turn`'s `turnStart.request` reaches `turn/start` unchanged; per-turn `approvalsReviewer`,
  `approvalPolicy` and `sandboxPolicy` apply and the user's next turn restores the selector's values.
- `approvalsReviewer: "user"` with a workspace-write sandbox does not prompt for writes inside the project; a read-only
  sandbox is needed for the approval card.
- Under the gate every `agent_relay` MCP tool asks for approval unless its `approval_mode = "approve"` is set.
- The MCP card's "始终允许" writes `[mcp_servers.agent_relay.tools.<tool>] approval_mode = "approve"` to
  `config.toml` (global, per tool). The terminal card has no "始终允许"; "允许类似命令" appends
  `prefix_rule(pattern=[<full command>], decision="allow")` to `~/.codex/rules/default.rules` (global, exact prefix).
- No pre-turn signal shows the overrides were applied; only the rollout's `thread_settings_applied` / `turn_context`
  afterwards, written about one second after the start-turn receipt.
- Choosing a thread by file time picked a real thread of another project once (Codex declined the request, nothing
  changed); every probe afterwards used the exact session id.

## Findings

E1. **A Codex name registered with `wake: null` is unknown to the bridge** (product). The bridge records the host only
with a wake binding, so messages to such a name queue silently. Expected: record the proven host at registration, or
warn the sender when the recipient's host is unknown.

E2. **The undelivered-Codex notification is not reliably visible** (product). `osascript display notification`
succeeds without showing anything on this Mac (notification permission or Focus), yet the bridge reports the user as
notified. Expected: word it as an attempt, give the user a place that always shows pending Codex messages (doctor /
`collab`), and let doctor check or explain the notification permission.

Both are scheduled for the next version together with a CI workflow (user decision, 2026-10-08).
