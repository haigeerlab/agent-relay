## Findings

1. Environment (Codex 0.160): a user-level plugin cannot be disabled per project or per session, so a Codex
   session in a project that wants agent-relay alone still loads Spec Guard when both are installed for the user.
   Both plugins also expose the same skill names (`collab`, `session-routing`, `session-delegation`,
   `collaboration-ops`) while guide Spec Guard 0.49.0 is installed, which can misroute natural-language triggers.
   Disappears once users run the split Spec Guard; until then document it in the migration guide. Owner:
   migration document (Spec Guard `collaboration-dependency`).
2. Ordering constraint: `state_migration.py` refuses a target mailbox that already has agents or messages (D14),
   so D7 (real migration) must run right after the runtime install and before any registration in D2–D3.
3. Environment (Claude): disabling the Spec Guard plugin per project does not remove user-level MCP servers
   that the guide 0.49.0 setup registered (`spec-guard-native-collaboration`, `spec-guard-local-ledger`), so a
   design-project session still sees the old mailbox beside agent-relay's. Expected to clear after migration,
   when the old host entries are removed with Spec Guard's uninstall; recheck D1 then. Owner: migration
   document.
