## Findings

1. Environment (Codex 0.160): a user-level plugin cannot be disabled per project or per session, so a Codex
   session in a project that wants agent-relay alone still loads Spec Guard when both are installed for the user.
   Both plugins also expose the same skill names (`collab`, `session-routing`, `session-delegation`,
   `collaboration-ops`) while guide Spec Guard 0.49.0 is installed, which can misroute natural-language triggers.
   Disappears once users run the split Spec Guard; until then document it in the migration guide. Owner:
   migration document (Spec Guard `collaboration-dependency`).
2. Ordering constraint: `state_migration.py` refuses a target mailbox that already has agents or messages (D14),
   so D7 (real migration) must run right after the runtime install and before any registration in D2–D3.
3. Environment (Claude): disabling the Spec Guard plugin per project does not remove user-level MCP servers
   that the guide 0.49.0 setup registered (`spec-guard-native-collaboration`, `spec-guard-local-ledger`), so a
   design-project session still sees the old mailbox beside agent-relay's. Expected to clear after migration,
   when the old host entries are removed with Spec Guard's uninstall; recheck D1 then. Owner: migration
   document.

4. Operator tooling (not product): driving the Codex App approval card from a background session is
   unreliable — AXPress on 允许一次 does nothing, Return lands on whichever control holds focus (once it opened
   the permission selector, once it apparently chose 始终允许). Future runs: the user clicks approvals, or the
   guide verifies `~/.codex/config.toml` after each approval.

5. Product (Spec Guard `collaboration-dependency`, unreleased): the Claude probe reports `not-installed` for a
   project that is a git worktree, because the host keeps that worktree's local `enabledPlugins` in the main
   checkout's `.claude/settings.local.json` (observed: installing in `cranky-allen-f2237a` created
   `spec-guard-plugin/.claude/settings.local.json` with only that key). Also blind to `--plugin-dir` sessions.
   Blocks D6 for any user who works in worktrees.

6. Product (agent-relay `uninstall-codex`, inherited from Spec Guard; target module `safe-uninstall`): Codex
   writes `[mcp_servers.<name>.tools.<tool>] approval_mode = "approve"` when the user picks 始终允许, and the
   exact-match uninstaller then treats the managed table as user-edited and refuses. Safe, but a normal host
   action blocks a clean uninstall; agent_relay already carries five such subtables from this run. Hardening
   should recognise host-written approval subtables (and say which lines differ).
