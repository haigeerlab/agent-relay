## Findings

R2-1. **doctor probes with PATH's `node`, not the node the host entries pin** (product, `ops-commands` follow-up).
Both host entries start the bridge with `/Users/vilin/.nvm/versions/node/v24.18.0/bin/node`; `doctor` runs
`--node node` by default, which in a shell whose PATH resolves to nvm v12.22.12 fails on `?.` and reports
`probe: fail` for a runtime that works. Expected: probe with the attached entry's command (or say which node it
used).

R2-2. **The Codex App approval selector does not reach `config.toml`** (host behaviour on App 26.930.61225;
`identity-check` / `ops-commands` guidance). The user set the selector to 请求批准; `approvals_reviewer` stayed
`guardian_subagent`, so doctor kept warning and wake binding would be refused. doctor's next step ("set the
selector; never edit the file for the user") does not resolve it; the user had to edit the file. Same symptom was
noted during delegation-fixes.

R2-3. **The preflight launch line swallows a trailing prompt** (operator hazard, acceptance kit). `--allowedTools`
is variadic on Claude Code 2.1.291, so a prompt appended after the printed command is taken as a tool name and the
background session starts idle with no prompt. Put the prompt before the options; preflight should print it that
way.

R2-4. **Two new 始终允许 subtables appeared during B4** (host behaviour, unexplained; `safe-uninstall` covers the
cleanup). After B4, `~/.codex/config.toml` gained `[mcp_servers.agent_relay.tools.bridge_send]` and
`[...bridge_wake_status]` with `approval_mode = "approve"`. The guide clicked one approval card, aimed at 允许一次;
no card for `bridge_wake_status` was seen. Round 1 recorded the same symptom. From then on S1's sends ran without a
card. During the D8/D9 routing runs two more appeared (`bridge_outbox`, `bridge_sessions`), again with only 允许一次 clicked; D17 removed all nine.

R2-5. **Codex ran a stale agent-relay copy** (operator setup error, with an acceptance-kit gap). Codex loads the
plugin from its own cache `~/.codex/plugins/cache/agent-relay-marketplace/agent-relay/0.1.0`, which was copied at
02:13 (round-1 era: no `bridge/`, no doctor, `--expires-at` integer-only); `status` there said
`native runtime revision does not match the audited commit`. The first Codex-origin create therefore failed with
`native collaboration runtime is not ready; install it explicitly first` and left envelope `r2-cc-wt` in `creating`.
preflight printed the marketplace source path, not the cache Codex actually runs, so it did not show this. The
runtime upgrade was done without refreshing the Codex plugin (the round-2 prep constraint required both). Fixed at
21:04 by the guide (user-authorized): `codex plugin add agent-relay@agent-relay-marketplace` re-copied the cache
from the main checkout (ef77d7f; only the host's `migrated-command-skills` differs), `config.toml` unchanged
(backup in the guide scratchpad). B rows are unaffected (mailbox tools come from the upgraded runtime server).
preflight should compare the installed cache with the source.

R2-6. **A delegated Claude target can answer before its mailbox MCP is connected, and then never returns the
result** (product, `session-delegation` / Claude adapter). Each create or continue starts the background Claude
process afresh (new pid and `startedAt`; its `--mcp-config` bridge starts with that process). The bridge server
itself starts in under a second, but Claude Code connects MCP servers asynchronously, so a quick task is answered
while `agent-relay` is still "connecting": the target says so, does not register or send, and stops. The origin
waits for nothing; the host then lists the target `status=idle`, `state=working`, which the controller's idle rule
treats as busy (`held` `target-busy`, the round-1 finding 4 symptom), or `status` reports
`mailbox-registration-missing`. Seen on the plain-repository second round and on the first round of `r2-cc-c4`;
the worktree rounds happened to connect in time. Expected: the target waits for the mailbox tools (or the envelope
tells it to retry once they appear) before answering, so the result route is always used.
